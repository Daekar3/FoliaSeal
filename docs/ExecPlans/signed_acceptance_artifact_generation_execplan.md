## Purpose / Big Picture

FoliaSeal’s signed-output acceptance checks need local PDFs, a signing identity, and JSON scenario manifests before the automated matrix harness can produce evidence. Those files live under `artifacts/`, which is intentionally ignored by git, so a fresh workspace currently cannot regenerate the acceptance inputs from tracked code. After this change, a contributor can run one tracked script to create the current acceptance assets, then run the existing signed matrix command to produce fresh evidence from current code rather than restoring defunct artifacts.

This is a tooling and evidence-enablement slice. The source-controlled change is the generator, tests, and documentation. The generated files under `artifacts/` are allowed working-tree outputs but must remain untracked.

## Context and Orientation

The relevant acceptance assets are named in `src/foliaseal/application/qa_signed_acceptance_assets.py`. The source PDF path is `artifacts/generated_acceptance_assets/signed_acceptance_fixture.pdf`, the signing identity path is `artifacts/generated_acceptance_assets/signed_acceptance_identity.p12`, and the three manifest paths are under `artifacts/preview_sweep_assets/`: `signed_acceptance_matrix.json`, `signed_preview_parity_matrix.json`, and `signed_fit_rejection_matrix.json`.

A PKCS#12 identity is a password-protected certificate bundle used here by the signing backend during tests and matrix runs. The passphrase for this local QA identity is `secret`, matching the README’s representative command. The identity is not a production certificate; it only allows the automated harness to create signed PDFs in a repeatable local environment.

The matrix harness is implemented in `src/foliaseal/presentation/qt/phase3_harness.py`. It loads each scenario, applies appearance overrides such as `layout_template`, `stamp_position`, `visible_fields`, `image_stamp_path`, `text_style`, `box_style`, and `signature_rect`, then either expects a successful signed output or an intentional validation rejection. The manifests produced by this slice must set explicit `expected_outcome` values so the harness can distinguish real failures from deliberate negative tests.

## Plan of Work

Add a new application module, `src/foliaseal/application/qa_signed_acceptance_generation.py`, that builds the fixture PDF, PKCS#12 identity, a small stamp image, and the three JSON manifests. The module should expose pure manifest builder functions and one write function that accepts an output root or explicit base directory so tests can use `tmp_path` without writing to the repository’s real `artifacts/` directory.

Add `scripts/generate_signed_acceptance_assets.py` as a thin command-line wrapper around that module. It should write to the canonical paths by default and print the paths it created. Re-running the script should overwrite only those known generated files.

Add focused unit tests in `tests/unit/test_qa_signed_acceptance_generation.py`. The tests should generate into a temporary directory, parse the PDF with the project’s PDF reader, parse the PKCS#12 bundle with `cryptography`, load all three manifests through the existing `_load_preview_matrix_manifest()` helper, and assert the currently documented scenario families, counts, fixture roles, timestamping mode, and expected outcomes.

Update `README.md` near the signed-output acceptance section to show the generator command before the existing matrix command. The README must state that the generated artifacts are local evidence inputs and are intentionally ignored by git.

After implementation, run the generator into `artifacts/`, run the focused tests, run the artifact-gated manifest tests that were previously skipped, and attempt the signed matrix commands that are practical in this workspace. Record exact outcomes in this plan.

If the acceptance matrix passes quickly, also run the two companion manifests into separate generated output directories. If a full matrix run exposes a scenario geometry issue, adjust only the generator’s scenario definitions and rerun the focused failing command.

## Validation and Acceptance

This slice is accepted when the generator creates all five canonical inputs from current source code, the unit tests prove those inputs are parseable and match the expected manifest contract, and the existing artifact-gated tests no longer skip when the generator has been run locally. The strongest acceptance evidence is a matrix `summary.json` reporting `acceptance_expectations_passed: true` and `expected_outcome_mismatch_count: 0` for each generated manifest that is run.

## Idempotence and Recovery

The generator is safe to rerun. It overwrites only the known generated PDF, PKCS#12 identity, stamp image, and manifest files under `artifacts/`. The matrix commands write run outputs under separate `artifacts/*_generated` directories. If a matrix run fails halfway, rerun the generator and rerun the matrix into a fresh output directory. Do not commit generated files from `artifacts/`.
